# 验收演示（5–8分钟）

先按README编译。在OMNeT++自带终端进入工程simulations目录。演示沿用正式40 s失效、60 s停发、70 s结束参数，不把缩短实验的结果写成正式统计。

```bash
mkdir -p ../results/demo
../isl.exe -u Qtenv -c IslBaseline --seed-set=0 --output-scalar-file=../results/demo/baseline.sca
```

1. 展示网络正常发送：运行/暂停/加速，24节点绿色，包逐跳转发。结束后基线1440/1440，440 ms，5.333跳。
2. 展示随机与定向：分别运行下面配置。40 s时6节点变色，连线保留但逻辑不可用。当前seed结果不等于20次均值；报告均值取final-20261105/raw_summary.csv。

```bash
../isl.exe -u Qtenv -c IslRandomFailure --seed-set=0 --output-scalar-file=../results/demo/random.sca
../isl.exe -u Qtenv -c IslFailure --seed-set=0 --output-scalar-file=../results/demo/target.sca
```

3. 打开 `results/final-20261105/figures/pdr_random_vs_targeted.png`：随机/定向失效后PDR均值67.12%/10.05%，LCC17.85/9；误差棒SD。再打开扫描曲线，指出k=5→6定向断崖。
4. 展示可恢复案例，只让S8失效，网络仍连通。观察S11→S23改道；可用下一跳表和包日志核对。完整过程图是实际日志重绘。

```bash
../isl.exe -u Qtenv -c IslReroute --seed-set=0 --output-scalar-file=../results/demo/reroute.sca
```

打开 `reroute_paths.png` 和 `reroute_timeline.png`：

- 旧路径：11–10–9–8–15–23。
- 新路径：11–12–13–14–15–23。
- 40 s失效、42 s更新、42.40 s首个更新后包送达，故这一流恢复间隔2.40 s；2 s是更新等待输入。
- 更新开/关的单节点失效后PDR为93.17%/69.57%。目的节点失效的流依然不能恢复。

5. 打开 `performance.png`：基线168.52 kbps，随机139.23 kbps，定向113.99 kbps，统计窗统一0–70 s。用发送/接收数和业务完成率解释源停发损失。
6. 展示源码、运行配置和 `verification.json`。说明507次核验通过，随机配对20个seed失效集合相同。

## 答辩要点

| 问题 | 准确回答 |
|---|---|
| 实际导航定位效果？ | 本课题评估通信可用性，未实现定位解算。 |
| 为什么定向20次一样？ | 选点固定、CBR确定，seed未引入其他随机源。 |
| 为什么不更新时平均时延也不差？ | 成功包多在失效前，需结合交付量，不能只看成功样本时延。 |
| 为什么大k时全程PDR回升？ | 失效源停发使分母减少，且失效前成功包占比上升；看同批PDR及固定需求完成率。 |
| 恢复能解决分区吗？ | 只能改走已有存活路径，不能凭空创建连边或修复端点。 |
| 是否测了拥塞？ | 当前仅固定传播时延，没有队列和容量约束。 |
| 40.1 s边界检查说明什么？ | 旧接收截点差450含18个旧包，新同批统计432/460=93.913%。 |
